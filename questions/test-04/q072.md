## Énoncé et corrigé fourni


You have an Azure subscription named Sub1 with the subscription ID 8f3a1c92-5d47-4b6e-a2f9-71c3d8e5ab40.
You want to create a custom Azure RBAC role named CustomRole1 that meets the following conditions:
- The role can be assigned only at the resource group scope within Sub1.
- The role must not allow users to manage access permissions (RBAC) on the resource groups.
- The role must allow users to view, create, update, and delete resources inside the resource groups.
You are defining the role by using a JSON definition that includes the assignableScopes and permissions sections.
What value should you specify for `Code Segment B` in the definition of CustomRole1?
Réponses:
**☑** "Microsoft.Authorization/"
☐ "Microsoft.Resources/"
☐ "Microsoft.Security/*"
Explication
`"Microsoft.Authorization/"` is the correct answer here. In the context of custom RBAC role definitions, the "notActions" element (Dropdown 2) is used to explicitly deny certain management operations, even if the `"actions"` list includes a wildcard like `"*"`. In this scenario, the custom role CustomRole1 must allow full access to view, create, modify, and delete resources within resource groups, but it must prevent the user from managing access permissions (i.e., prevent role assignments).
Role assignment and access control operations in Azure are managed through the Microsoft.Authorization namespace. Therefore, to block permission management, you need to specify "Microsoft.Authorization/" in the "notActions" array. This removes the ability to read, create, or delete role assignments, while still allowing other actions.
`"Microsoft.Resources/"` is incorrect because this namespace is used for general resource management tasks like creating and managing resource groups or deployments, not for managing access control. Including it in "notActions" would block legitimate resource operations that the role should be allowed to perform.
`**"Microsoft.Security/*"` is incorrect** because it relates to security center operations such as policy management, security recommendations, and alerts. It is not relevant to access control and does not affect permissions related to RBAC.
