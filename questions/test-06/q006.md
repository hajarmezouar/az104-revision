## Énoncé et corrigé fourni


Your environment includes an on-premises Active Directory Domain Services (AD DS) domain with the identities listed below:
- User1 is a user account located in OU2.
- User2 is a user account located in OU1.
- Group1 is a global security group that includes User1 and is located in OU1.
You have an Azure subscription that contains a storage account named storage1.
The Azure Files shares in storage1 use AD DS as the identity source, and the default share-level permissions are configured to allow access for all authenticated users and groups.
You create an Azure Files share named share1 and assign the following roles:
- User2 is assigned the Storage File Data SMB Share Reader role.
- Group1 is assigned the Storage File Data SMB Share Contributor role.
You also have a Microsoft Entra tenant that includes a cloud-only user named User3.
Microsoft Entra Connect is configured to synchronize OU1 from the on-premises AD DS domain to the Microsoft Entra tenant.
True or False:
`“User1 is able to access the data stored in share1.”`
Réponses:
**☑** True
☐ False
Explication
`True` is the correct answer because User1 can access share1 by using AD DS authentication, even though User1 is not synchronized to Microsoft Entra ID.
The storage account uses AD DS as the identity source, and default share-level permissions are enabled for all authenticated users and groups. For Azure Files with AD DS authentication, Microsoft states that when a default share-level permission is configured, on-premises AD DS identities do not need to be synchronized to Microsoft Entra ID. The identity only needs to authenticate against the AD DS deployment associated with the storage account.
In addition, User1 is a member of Group1 in the on-premises AD DS domain. Group1 is located in OU1, is synchronized to Microsoft Entra ID, and has the Storage File Data SMB Share Contributor role on share1. Microsoft states that for AD DS authentication, non-synchronized users can still access Azure file shares through membership in a synchronized AD DS group. Azure Files reads the group SIDs from the user’s Kerberos ticket and applies the matching RBAC role assignments.
Therefore, User1 can access the data in share1, assuming the applicable NTFS/file-level permissions do not deny access. Azure Files evaluates both share-level permissions and Windows ACLs, and the most restrictive permission applies.
