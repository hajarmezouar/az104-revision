## Énoncé et corrigé fourni


Note: This question is part of a series that uses the same overall scenario. Each question in the series proposes a different solution that may or may not satisfy the stated requirement.
You have an application named App1 that runs on two Azure virtual machines, VM1 and VM2. Incoming traffic to App1 is handled through an Azure Load Balancer. The effective network security rules applied to VM2 are shown in the exhibit.
You observe that connection attempts from the IP address 131.107.100.50 to App1 over TCP port 443 are unsuccessful, even though the Load Balancer rules have been confirmed to be correctly configured.
You want to ensure that traffic from 131.107.100.50 can successfully reach App1 on port 443.
Proposed Solution: You remove the inbound network security rule named BlockAllOther443.
Does this solution achieve the stated objective?
Réponses:
**☑** Yes
☐ No
Explication
`Yes` is correct because the inbound security rule Block_All_Other_443 (priority 200) denies all TCP 443 traffic from any source to any destination. This rule inadvertently blocks the Azure Load Balancer’s health probe traffic, which also uses TCP 443. Since health probes are required to mark backend VMs as healthy, VM2 is excluded from the load balancer rotation, causing all client traffic (even from 131.107.100.50, which is explicitly allowed by rule 100) to fail. By deleting the overly broad deny rule, the health probe is allowed through via the built-in AllowAzureLoadBalancerInBound rule (priority 65001), restoring VM2’s healthy state. Once the probe succeeds, the client IP 131.107.100.50 can connect successfully because its explicit allow rule (priority 100) is already in place.
